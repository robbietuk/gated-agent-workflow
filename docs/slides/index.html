Six methods for the branch code review

Whole branch vs design

Catches drift between slices, duplicated logic and anything that misfits the design.

Parallel narrow lenses

Safety, concurrency, errors, compatibility, traceability. Sized to the diff: one reviewer for a few lines, one per lens and file group for a big branch.

Verify pass

A second agent must show the failing inputs and state. Unconfirmed findings are dropped.

Severity ranking

Blockers escalate. Important issues get fixed. Nits are fixed automatically.

A second model

A different model from the one that wrote the code catches different mistakes.

Test adequacy

Every req ID has a test that fails if its code is removed.

Evidence

What teams already doing this learned

Short artifacts steer better

A ~200-line design and a two-page outline beat an eight-page plan that drifts from the code.

Keep research objective

Research mixed with the intended solution loses its objectivity. Give it questions only.

Keep reading the code

Skipping code review “did not end well”. Reviewing the plan doesn’t prove the code matches it.

Revert and replan

When a run goes off track, a sharper plan and a re-run is often faster than patching.
